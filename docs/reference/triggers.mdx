Triggers define the event that starts your workflow. Each trigger is tied to an integration and fires when a specific event occurs. Your `onTrigger` handler receives a typed event object with the payload.

## Integration triggers

### GitHub

| Trigger                   | Event type          | Description                |
| ------------------------- | ------------------- | -------------------------- |
| `GitHub.onPROpened()`     | `GithubPRTrigger`   | A pull request is opened   |
| `GitHub.onPush()`         | `GithubPushTrigger` | Code is pushed to a branch |
| `GitHub.onIssueCreated()` | `GithubTrigger`     | An issue is created        |

**Config:** Scoped to specific repositories via `repo` parameter.

<CodeGroup>
```ts TypeScript
triggers: [GitHub.onPROpened({ repo: Repos.MyOrg.MyRepo })]
```
```python Python
triggers=[
    TriggerConfig(
        integration_id=github_integration_id,
        integration_type="github",
        config_type="github",
        config={
            "repositoryIds": [repo_id],
            "eventTypes": ["pull_request.opened"],
        },
    )
]
```
</CodeGroup>

<Expandable title="Event payload">

**All GitHub events include:**

- `repository` - `{ id, name, owner, defaultBranch }`
- `sender` - `{ login, email }`
- `commits` - array of `{ sha, message, fileDiffs: [{ filename, diff }] }`

**PR events add:**

- `pullRequest` - `{ number, title, body, state, merged, head, base, author, url }`

**Push events add:**

- `branch` - the branch that was pushed to

</Expandable>

### Slack

| Trigger             | Event type     | Description                      |
| ------------------- | -------------- | -------------------------------- |
| `Slack.onMessage()` | `SlackTrigger` | A message is posted in a channel |
| `Slack.onDm()`      | `SlackTrigger` | A direct message is received     |

**Config:** Scoped to specific channels or users.

<CodeGroup>
```ts TypeScript
triggers: [Slack.onMessage({ channel: SlackChannel.Engineering })]
```
```python Python
triggers=[
    TriggerConfig(
        integration_id=slack_integration_id,
        integration_type="slack",
        config_type="slack",
        config={"channelId": SlackChannel.Engineering.channel_id},
    )
]
```
</CodeGroup>

<Expandable title="Event payload">
  - `channelId`, `channelName` - where the message was posted
  - `userId`, `userName` - who sent it
  - `text` - message content
  - `timestamp` - Slack message timestamp (also the thread parent timestamp when the message is in a thread)
  - `channelType` - `"channel"`, `"group"`, `"mpim"`, or `"im"`
  - `files` - array of attached files with `{ id, name, mimetype, url_private }`
  - `attachments` - rich message attachments
</Expandable>

**Config:** Filtered by event types (`user.created`, `organization.created`, `organization_membership.created`, `invitation.created`, etc.).

</CodeGroup>

<Expandable title="Event payload">

### Web Monitor

| Trigger                  | Event type          | Description                                                  |
| ------------------------ | ------------------- | ------------------------------------------------------------ |
| `WebMonitor.onEvent()`   | `WebMonitorTrigger` | Fires when scheduled web monitoring detects relevant changes |

Terse creates and manages the underlying monitor. You define the query and how often to check; your agent runs whenever new relevant content is detected.

**Config:** A natural-language `query` describing what to track, and a `frequency` specifying how often to check.

<CodeGroup>
```ts TypeScript
triggers: [
  WebMonitor.onEvent({
    query: "Acme Corp funding announcements or acquisitions",
    frequency: { number: 1, unit: "day" },
  }),
]
```
</CodeGroup>

<Expandable title="Event payload">
  - `query` - the monitoring query that fired
  - `frequency` - `{ number: number, unit: "h" | "d" | "w" }` — the configured check interval
  - `monitorId` - the Parallel monitor id that fired
  - `eventGroupId` - the Parallel event group id for this detection
  - `metadata` - string metadata echoed back from monitor creation
  - `payload` - the fetched event payload for this trigger; typed from `outputSchema` when provided, otherwise a string
  - `rawPayload` - the raw text output for the event; only present when `outputSchema` is used
  - `outputType` - `"text"` or `"json"`
  - `eventDate` - the event date from Parallel
  - `sourceUrls` - source URLs for the detected event
</Expandable>

#### Writing effective queries

The monitor matches by intent, not keywords. Write your query as a natural sentence describing what you care about — not a search string.

**Do:**
- Write in plain language: `"Acme Corp product launches or pricing changes"`
- Be specific about subject and signal: `"FDA approval decisions for GLP-1 drugs"`
- Combine related signals: `"OpenAI or Anthropic model releases and benchmark results"`

**Don't:**
- Use Boolean operators (`AND`, `OR`, `NOT`) — this is not a search engine
- Include specific dates — monitors track new developments going forward, not history
- Write keyword dumps: `"acme corp acme funding raise series B"`

**Choosing frequency:**

| Frequency | Best for                                                        |
| --------- | --------------------------------------------------------------- |
| `1h`      | Breaking news, social signals, fast-moving markets              |
| `1d`      | Press releases, blog posts, job postings, pricing page changes  |
| `1w`      | Regulatory filings, quarterly reports, slow competitive signals |

For historical research (what happened in the past), use a research task rather than a monitor.

#### Testing on demand

Web Monitor triggers fire on a schedule, but you don't have to wait for the first real detection to test your agent. Use **Run with sample event** in the dashboard to fire a synthetic event immediately — paste in a representative `payload` and iterate on your agent logic before the first live detection arrives.

## System triggers

### Schedule

| Trigger           | Event type    | Description              |
| ----------------- | ------------- | ------------------------ |
| `Schedule.cron()` | `CronTrigger` | Fires on a cron schedule |

<CodeGroup>
```ts TypeScript
triggers: [Schedule.cron("0 9 * * 1")] // Every Monday at 9am
```
```python Python
triggers=[Schedule.cron("0 9 * * 1")]  # Every Monday at 9am
```
</CodeGroup>

<Expandable title="Event payload">
  - `data.isManualTrigger` - whether the run was triggered manually from the dashboard
  - `data.manualContext` - optional context string provided on manual triggers
</Expandable>

### Webhook

| Trigger               | Event type       | Description                                               |
| --------------------- | ---------------- | --------------------------------------------------------- |
| `Webhook.onRequest()` | `WebhookTrigger` | Fires when an HTTP request hits the generated webhook URL |

Webhook URLs are auto-generated on deploy and remain stable across redeploys.

Pass a type argument to `Webhook.onRequest<YourPayload>()` so `onTrigger` and `filter` see your JSON body shape on `event.body` (defaults to `unknown` when omitted).

<CodeGroup>
```ts TypeScript
triggers: [Webhook.onRequest()]
```
```python Python
triggers=[
    TriggerConfig(
        integration_id="system",
        integration_type="webhook",
        config_type="webhook_input",
        config={},
    )
]
```
</CodeGroup>

<Expandable title="Event payload">
  - `body` - parsed JSON request body (typed when you use `Webhook.onRequest<...>()`)
  - `headers` - HTTP headers
  - `method` - HTTP method (GET, POST, etc.)
</Expandable>

## Common event interface

All triggers resolve to the shared canonical `Trigger` payload shape. Your handler receives the concrete subtype for the trigger you selected.

<CodeGroup>
```ts TypeScript
interface Trigger {
  readonly integrationType: string
  readonly eventType: string
}
```
```python Python
class Trigger:
    integration_type: str
    event_type: str
```
</CodeGroup>

Each trigger subtype adds its own canonical fields, such as Slack message metadata, GitHub PR data, webhook request bodies, or cron trigger context.
