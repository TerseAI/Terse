The `terse` CLI scaffolds, generates, tests, runs, and deploys Terse projects in both TypeScript and Python.

All commands auto-detect the project language from the current directory based on marker files.

| Language   | Project markers                 | Entry file     | Generated file           |
| ---------- | ------------------------------- | -------------- | ------------------------ |
| TypeScript | `package.json`, `src/index.ts`  | `src/index.ts` | `src/terse.generated.ts` |
| Python     | `pyproject.toml`, `src/main.py` | `src/main.py`  | `src/terse_generated.py` |

Python projects require [`uv`](https://docs.astral.sh/uv/getting-started/installation/) for dependency management and local execution.

## `terse init [project-name]`

Scaffolds a new project and runs the full setup flow: installs dependencies, authenticates, connects integrations, and generates your SDK.

<CodeGroup>
```bash TypeScript
terse init my-project
```
```bash Python
terse init my-project --language python
```
</CodeGroup>

**Options:**

| Flag                    | Description                           | Default |
| ----------------------- | ------------------------------------- | ------- |
| `-l, --language <lang>` | `ts`, `typescript`, `py`, or `python` | `ts`    |

**What it does in order:**

1. Creates the project directory and scaffolds files (config, `.gitignore`, entry file)
2. Detects your package manager (pnpm/npm for TypeScript, uv for Python) and installs dependencies
3. Runs `terse login` to authenticate
4. Runs `terse integrate` to check and connect integrations
5. Runs `terse generate` to produce your typed SDK

## `terse login`

Authenticates with Terse using a device authorization flow and writes `TERSE_API_KEY` to your project's `.env` file.

```bash
terse login
```

**How it works:**

1. Requests a device code from WorkOS
2. Opens your browser to a verification page
3. Polls until you complete the browser authorization
4. Exchanges the token with the Terse backend for an API key
5. Writes `TERSE_API_KEY` to `.env` (creates or updates)

If a valid API key already exists, you'll be prompted before re-authenticating.

## `terse integrate`

Connects third-party integrations to your Terse workspace from the CLI. After connecting, automatically re-runs `terse generate` to update your SDK.

```bash
terse integrate
```

**How it works:**

1. Fetches your currently connected integrations and displays their status
2. Prompts you to select an integration to connect
3. Walks you through the connection flow (varies by integration type)
4. Re-runs `terse generate` after any changes

**Connection types:**

| Type  | Flow                                                                  | Integrations                                     |
| ----- | --------------------------------------------------------------------- | ------------------------------------------------ |
| OAuth | Opens browser for authorization, polls until connected                | GitHub, Slack, Gmail, Linear, Notion, WorkOS     |
| Form  | Prompts for credentials (API keys, account IDs, etc.) in the terminal | Datadog, PostHog, Snowflake, LaunchDarkly, Attio |

## `terse generate`

Fetches your connected integrations and their resources from the Terse backend, then writes a typed SDK file for your project language.

```bash
terse generate
```

**Outputs:**

<CodeGroup>
```text TypeScript
src/terse.generated.ts
```
```text Python
src/terse_generated.py
```
</CodeGroup>

**What's in the generated file:**

| Category                    | Examples                                                                                                    |
| --------------------------- | ----------------------------------------------------------------------------------------------------------- |
| Resource constants          | `Repos.MyOrg.MyRepo`, `SlackChannel.Engineering`, `AttioList.Deals`                                         |
| Trigger builders            | `GitHub.onPROpened()`, `Slack.onMessage()`, `Schedule.cron()`, `Webhook.onRequest<BodyType>()` (TypeScript) |
| Skill constructors          | `GitHub.skill()`, `Slack.skill()`, `Attio.skill()`                                                          |
| Deterministic tool wrappers | `agent.tools.slack.sendMessage()`, `agent.tools.attio.queryRecords()`                                       |

Each integration generates typed helpers based on the actual resources in your workspace (repos, channels, lists, projects, etc.), so your code references real names instead of raw IDs.

TypeScript projects also get `Webhook` from `src/terse.generated.ts`. Pass a type argument to `Webhook.onRequest<YourBodyType>()` so `onTrigger` and `filter` infer `WebhookTrigger<YourBodyType>` for `event.body`. See [Webhook trigger](/reference/triggers#webhook).

**When to re-run:**

- After connecting or disconnecting an integration
- After adding resources to a connected integration (new Slack channel, new GitHub repo, etc.)
- After upgrading `terse-cli` (new tool definitions may be available)

## `terse test [job-name]`

Fetches real sample events from the Terse backend and runs your job locally against a selected event.

```bash
terse test
terse test my-job
```

**Options:**

| Flag            | Description                             | Default |
| --------------- | --------------------------------------- | ------- |
| `-v, --verbose` | Show agent stream output during the run | Enabled |

**How it works:**

1. Loads your job registry from the entry file
2. Fetches sample events from the backend for integration-based triggers (e.g. real GitHub PR events, real Slack messages)
3. Generates synthetic events for cron and webhook triggers
4. Prompts you to select an event
5. Executes your job's `onTrigger` handler locally

If you only have one job, it's selected automatically.

## `terse run [job-name]`

Runs a job locally with an explicit event payload. Unlike `test`, this is non-interactive and does not fetch sample events.

Pass a **serialized event**: JSON with `integrationType`, `eventType`, `formattedContent`, `debugLog`, and `data`. The `data` field is the full canonical trigger object (the same discriminated shape live runs use). Use `terse test` and inspect a sample, or copy the structure from Activity when debugging.

Alternatively, set `TERSE_RUN_ID` to a run ID from [Activity](/core-concepts/activity-and-observability) and omit `--event` / `--event-file`. The CLI fetches that run’s serialized trigger event from the Terse backend (the same payload shape a live run would pass to `onTrigger`).

```bash
terse run my-job --event-file ./event.json
```

Example `event.json` for a manual cron-style run (`formattedContent` and `debugLog` should match what the platform would produce for the same `data` payload):

```json
{
    "integrationType": "cron_job",
    "eventType": "cron",
    "formattedContent": "This is a manually triggered event for the channel input trigger_123.\n\nUser provided context for this manual trigger:\nManual trigger",
    "debugLog": "Manual Trigger",
    "data": {
        "integrationType": "cron_job",
        "eventType": "cron",
        "inputId": "trigger_123",
        "isManualTrigger": true,
        "manualContext": "Manual trigger"
    }
}
```

**Options:**

| Flag                  | Description                                         |
| --------------------- | --------------------------------------------------- |
| `--event <json>`      | Inline serialized event JSON                        |
| `--event-file <path>` | Path to a JSON file containing the serialized event |

Provide `--event` or `--event-file`, or set **`TERSE_RUN_ID`** in the environment so the CLI can load the serialized trigger event for that run from the backend.

## `terse replay [run-id]`

Replays a past run on your machine: fetches the serialized trigger event for the given run ID and executes that workflow’s `onTrigger` locally (with verbose agent output). Use the run ID from the Activity list or run drawer.

```bash
terse replay run_abc123
```

This complements **Re-trigger** in the Terse app, which runs the workflow again on the platform with the same trigger payload.

## `terse history [job-name]`

Lists past runs for a **deployed** workflow (the CLI matches your local job name to the agent on Terse). Optionally enriches each row with the input trigger payload or the full stored model stream.

Use **`--json`** when you need machine-readable output for scripts or agent tooling. Use **`--triggers`** to attach each run’s serialized trigger event (the same shape a live run passes to `onTrigger`). **`--events`** fetches the full conversation per run (heavier; includes the trigger payload).

```bash
terse history my-job
terse history my-job --json --triggers
terse history --run-id run_abc123
```

**Options:**

| Flag | Description |
| ---- | ----------- |
| `--json` | Print JSON instead of a table |
| `--limit <n>` | Max runs to return (default 20, max 100) |
| `--page <n>` | Page number (1-indexed) |
| `--status <list>` | Comma-separated: `success`, `failed`, `cancelled`, `skipped`, `in_progress`, `awaiting_approval` |
| `--since <iso>` | Only runs at or after this ISO timestamp |
| `--until <iso>` | Only runs at or before this ISO timestamp |
| `--query <q>` | Free-text search across trigger, decision, and event fields |
| `--triggers` | Include the input trigger event JSON for each listed run |
| `--events` | Include the full model event stream for each listed run |
| `--run-id <id>` | Show chat events for one run instead of listing runs for a job |

## `terse deploy`

Packages your project and deploys all jobs to the Terse platform. [Learn more about how deployment works.](/hosting)

```bash
terse deploy
```

**What happens:**

- New jobs are created on the platform
- Existing jobs are updated (webhook URLs remain stable)
- Jobs removed from your code are removed from the platform
- Your entire project is zipped, uploaded, and hosted serverlessly

## Required environment variable

Commands that call the Terse API need **`TERSE_API_KEY`**. `terse login` writes it to `.env` in the project directory; when you run the CLI from that directory, it loads `.env` automatically. You can also **`export TERSE_API_KEY`** in your environment if the process cannot read `.env` (for example in a restricted sandbox).

`terse init` runs the full setup flow, including login. `terse login` only authenticates and updates `.env`.
