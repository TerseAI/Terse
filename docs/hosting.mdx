When you run `terse deploy`, your workflow goes from local code to a hosted, trigger-ready automation in seconds. There's no build step, no Dockerfile, and no infrastructure to configure.

## What happens when you deploy

<Steps>
    <Step title="Your code is zipped and uploaded">
        The CLI collects all project files (excluding `node_modules`, `.git`, `.env`, and other non-essentials), compresses them into a ZIP archive, and uploads it to cloud storage. Archives are
        content-addressed by SHA-256 hash, so identical code across deploys is automatically deduplicated.
    </Step>
    <Step title="Triggers and skills are registered">
        Each job's triggers (e.g. a GitHub webhook, a cron schedule) and skills (e.g. Slack, Apollo) are registered on the Terse platform. Webhook URLs remain stable across redeploys, so you never
        need to reconfigure external services. Any jobs from a previous deploy that are no longer in your code are automatically cleaned up.
    </Step>
    <Step title="A trigger fires">
        When an event matches one of your triggers, Terse spins up an isolated [Modal](https://modal.com) sandbox with the right runtime: `node:22-slim` for TypeScript, detected automatically from
        your `package.json`.
    </Step>
    <Step title="Your handler executes">
        Inside the container, your code is extracted, dependencies are installed, and your workflow runs with the serialized trigger payload. Your `onTrigger` handler executes. It can call tools
        deterministically, prompt the agent, or both. When the run completes, the container is torn down and results are logged.
    </Step>
</Steps>

## Security

Each execution runs in its own isolated [Modal](https://modal.com) sandbox with a **project-scoped**, short-lived API token that is removed when the run finishes (and may also carry an expiration time). Your code and credentials are never shared across runs or organizations.

## Hosted execution reliability

Terse may reuse a warm sandbox between runs. Before your handler runs, the platform verifies that the environment is actually ready; if a sandbox was terminated or left inconsistent, Terse replaces it and retries provisioning when things need a moment to settle. Your workflow code and the `terse-sdk` APIs you call from `onTrigger` stay the same—you do not add client-side retry logic for this.

## What gets uploaded

The CLI respects standard ignore patterns. The following are always excluded:

<Tabs>
    <Tab title="TypeScript">`node_modules`, `.git`, `dist`, `.next`, `.turbo`, `.env`, `.DS_Store`</Tab>
</Tabs>

Everything else in your project directory is included in the deploy.
